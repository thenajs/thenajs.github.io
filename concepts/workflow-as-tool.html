Workflow como Tool

Uma tool pode disparar um workflow inteiro. O filho roda com estado próprio e devolve uma string ao pai — é assim que se consegue isolamento de contexto sem escrever nada para isso.

o que acontece
agente pai  (histórico enxuto)
 │
 └─ tool ──▶ workflow isolado  (StateManager próprio)
              ├─ 10 turnos de tentativa e erro
              ├─ tools, loops, outros agentes
              └─ devolve UMA string ao pai
                          │
     ◀────────────────────┘
   o pai vê só o resultado, nada do caminho

Isso importa muito com modelo pequeno: o custo de um agente não é só token, é atenção. Dez turnos de tentativa e erro no histórico do pai degradam as decisões dele. Passando pelo filho, o pai recebe uma linha.

Como se escreve

O construtor da tool recebe o WorkflowRuntime injetado — é a única dependência injetável, e toda tool a recebe.

deploy.tool.ts
import { Tool, WorkflowRuntime } from "@thenajs/core";
import { DeployWorkflow } from "../workflows/deploy.workflow.js";

@Tool({
  name: "deploy",
  description: "Executa o processo de deploy e devolve o resultado.",
  schema: z.object({ repository: z.string() }),
})
export class DeployTool {
  constructor(private readonly runtime: WorkflowRuntime) {}

  async execute(input: { repository: string }) {
    // workflow completo: estado novo, histórico novo
    return this.runtime.run(DeployWorkflow, { input });
  }
}

Step ou workflow-tool? O guia de decisão

É a escolha arquitetural central do framework, e as duas formas parecem equivalentes até a primeira vez que você é mordido pela diferença.

Sub-agente como stepSub-agente como workflow-tool
Histórico compartilhado com o pai próprio, isolado
A saída vira mensagem assistant no transcript observação tool, como qualquer resultado
Quem decide se roda você, na ordem dos steps o modelo, chamando (ou não) a tool
Custo de contexto no pai todos os turnos do filho uma string
Use quando as etapas são uma conversa só e o pai precisa ver o caminho a subtarefa é ruidosa, ou o pai só precisa do resultado
⚠️ O modo mais comum de errar isso é montar steps: [PlannerAgent, loop([OrchestratorAgent])] esperando que o plano seja contexto para o orchestrator. Como step, ele vira fala do orchestrator — que então acha que já respondeu. Ou promova o plano a memory (veja Workflows) ou isole o planner atrás de uma tool.

O que o filho enxerga

O runtime.run cria um StateManager novo. O filho começa com o input que a tool passou como primeiro turno de usuário — e nada do histórico do pai. Se ele precisar de algum contexto do pai, isso tem que ir explicitamente, pelo input ou pelo memory: 

return this.runtime.run(DeployWorkflow, {
  input: { message: `Faça o deploy de ${input.repository}` },
  memory: { ambiente: "staging", autor: "ci-bot" },
});

Report e orçamento atravessam o isolamento de formas opostas

O report aninha. A execução do filho aparece como subárvore dentro do nó tool do pai, então você não perde a visibilidade que abriu mão no contexto: 

workflow WPai
  loop
    agent PaiAgent
      chat
        tool sub
          workflow WFilho      ← o filho aparece aqui
            agent FilhoAgent
              chat
⚠️ O orçamento não atravessa. Cada run tem o próprio contador. Um budget no pai não soma o consumo dos workflows-filhos — no exemplo acima o pai reporta 2 chamadas ao modelo, não 3.

Se o subworkflow é caro, passe um budget também no runtime.run dele. Um teto no pai sozinho não limita o total.
