Hooks

Métodos opcionais que a classe do agente declara para interceptar e manipular o fluxo padrão. O runtime chama só o que existir.

HookQuandoContrato
beforePrompt(prompt, ctx)antes de enviar ao modeloretorna o prompt (transforma)
beforeTool(call, ctx)antes da tooltroca os args, ou throw cancela
afterTool(result, ctx)depois da toolstring troca o texto (preserva isError); ToolOutput substitui tudo
afterResponse(response, ctx)na resposta do passoretorna a resposta (transforma)
onError(error, ctx)em erro no fluxoretorno vira fallback
Contrato dos transformadores: retornou um valor → substitui; retornou undefined → mantém o original.

Assinaturas exatas

Vale copiar daqui: os tipos de entrada e de retorno não são simétricos, e alguns nomes contrariam a intuição de quem vem da API da OpenAI.

AgentHooks
beforePrompt(prompt: string, ctx: AgentContext): string | void
beforeTool(call: ToolCall, ctx: AgentContext): ToolCall | void
afterTool(result: ToolResult, ctx: AgentContext): string | ToolOutput | void
afterResponse(response: string, ctx: AgentContext): string | void
onError(error: Error, ctx: AgentContext): string | void

// todos aceitam Promise<…> também

ToolCall   = { name: string; args: unknown }
ToolResult = { name: string; args: unknown; output: string; isError?: boolean }
ToolOutput = { content: string; isError?: boolean; data?: unknown }
⚠️ Dois tipos parecidos, e um retorno assimétrico.
O ToolCall dos hooks usa args. O que circula no ctx.turn e no report é o ProviderToolCall ({ id, name, arguments, source }), com arguments. São tipos diferentes de propósito: um é o que você intercepta, o outro é o que o provider produziu.

E o afterTool recebe um ToolResult mas não devolve um: devolva uma string (troca só o texto e preserva o isError) ou um ToolOutput completo.

Até a 0.2.0 os dois se chamavam ToolCall e o do engine era o que vinha no autocomplete errado. Desde a 0.3.0 ele é ProviderToolCall; o nome antigo segue como alias deprecado no @thenajs/agentflow.

Exemplo

com hooks
export class ExplorerAgent implements AgentHooks {
  async beforePrompt(prompt: string) {
    return `${prompt}\n\n[data] ${new Date().toISOString().slice(0, 10)}`;
  }
  async beforeTool(call: ToolCall) {
    const { command } = call.args as { command: string };
    if (/\brm\b|sudo/.test(command)) throw new Error("bloqueado"); // guardrail
  }
  async onError() {
    return "Não consegui completar agora."; // fallback
  }
}

Ordem de disparo

fluxo
beforePrompt → chat [ beforeTool → execute → afterTool ] → afterResponse
                                   (qualquer throw) → onError

Padrões que os hooks já resolvem

Duas coisas que parecem pedir API dedicada, mas que ficam melhores em user-land — porque a semântica certa depende do seu fluxo.

A saída de um passo como contexto, não como fala. Por padrão a resposta de um agente entra no transcript do próximo como mensagem assistant. Para que um plano vire contexto durável, reescreva o history no próprio agente — ctx.state é público:

planner.agent.ts
export class PlannerAgent implements AgentHooks {
  afterResponse(plano: string, ctx: AgentContext) {
    // tira o turno do transcript e promove para memória (vira `system` no topo)
    ctx.state.set("history", ctx.state.history.slice(0, -1));
    ctx.state.append("memory", `Plano:\n${plano}`);
    ctx.plan = plano;
  }
}

Cortar uma chamada repetida. beforeTool cancela a execução com um throw; combine com ctx.budget (veja Orçamentos de run) se quiser uma heurística que dependa do consumo: 

export class ExplorerAgent implements AgentHooks {
  private vistas = new Set<string>();

  beforeTool(call: ToolCall) {
    const assinatura = `${call.name}:${JSON.stringify(call.args)}`;
    if (this.vistas.has(assinatura)) {
      throw new Error(`Já chamei ${call.name} com esses argumentos.`);
    }
    this.vistas.add(assinatura);
  }
}

Escape hatch

Se a classe define run(input, ctx), ela assume o controle total do passo e os hooks automáticos não são chamados. Use quando quiser orquestrar você mesmo.
