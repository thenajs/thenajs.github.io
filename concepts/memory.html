Memória vetorial

Busca semântica: o agente grava textos e recupera por similaridade, não por ordem. É o par que faltava para o embed() dos providers.

⚠️ Não confunda com ctx.state.memory. Aquele é o bucket string[] de contexto durável que vira mensagem system no prompt (veja Estado & memória). Este aqui — ctx.memory, sem o state — é o banco vetorial. Nomes parecidos, coisas diferentes.

O nome da collection é a chave

Cada store aponta para uma collection, e o nome dela vira o acesso em ctx.memory.<collection>. Declare quantos precisar:

vector/stores.ts
import { QdrantStore } from "@thenajs/qdrant-client";

export const conhecimento = new QdrantStore({
  url: "http://localhost:6333",
  collection: "conhecimento",
});

export const cache = new QdrantStore({
  url: "http://localhost:6333",
  collection: "cache",
});

export const memorias = [conhecimento, cache] as const;
explorer.agent.ts
@Agent({
  provider: LocalOllamaProvider,   // o embed() dele gera os vetores
  memory: memorias,                // ← runtime
  prompt: "./explorer.agent.md",
})
export class ExplorerAgent implements AgentHooks<typeof memorias> {  // ← tipo

  async beforePrompt(prompt: string, ctx: AgentContext<typeof memorias>) {
    const pergunta = ctx.state.history.at(-1)?.content ?? "";

    const achados = await ctx.memory.conhecimento.recall(pergunta, {
      limit: 3,
      scoreThreshold: 0.5,
    });

    if (!achados.length) return;   // undefined mantém o prompt

    return `${prompt}\n\n## Contexto\n${achados.map((a) => `- ${a.text}`).join("\n")}`;
  }

  async afterResponse(resposta: string, ctx: AgentContext<typeof memorias>) {
    await ctx.memory.cache.remember(resposta);
  }
}

Por que o implements

ctx.memory.conhecimento tem autocomplete, e um typo não compila. Quem dá isso é o implements AgentHooks<typeof memorias> — o decorator sozinho não consegue.

Um class decorator tem assinatura (target) => void e o corpo da classe é checado independentemente dos argumentos dele. É a mesma razão pela qual @Agent({ tools: [ShellTool] }) não tipa nada sobre as tools dentro da classe. O implements, por fazer parte da declaração, carrega o tipo para os métodos.

⚠️ Passe instâncias, não classes. O nome da collection só é inferido na instanciação. Numa subclasse os type params são fixados no extends e o super() não os retroalimenta — você ficaria com collection: string e perderia o autocomplete sem perceber. É a diferença em relação ao provider, que aceita classe.

A API

// gravar
await ctx.memory.conhecimento.remember("o deploy roda pelo scripts/deploy.sh");
await ctx.memory.conhecimento.remember("nota", { payload: { tipo: "infra" } });
await ctx.memory.conhecimento.rememberMany([{ text: "a" }, { text: "b" }]);

// buscar
await ctx.memory.conhecimento.recall("como faço deploy?", { limit: 3 });
await ctx.memory.conhecimento.recall("q", { where: { tipo: "infra" } });
await ctx.memory.conhecimento.recall("q", { scoreThreshold: 0.5 });

// esquecer
await ctx.memory.conhecimento.forget({ where: { tipo: "infra" } });

O recall devolve { text, score, id, payload } ordenado por similaridade. O payload que você grava volta inteiro, e serve de filtro pelo where — é assim que se separa contexto dentro de uma collection (por tipo, por origem, por sessão) sem precisar de outro store.

⚠️ A collection guarda um size fixo, descoberto no primeiro remember pelo tamanho do vetor — 768 com nomic-embed-text, 1536 com text-embedding-3-small. Dois agentes com modelos de embedding de dimensões diferentes apontando para a mesma collection vão colidir, e o banco recusa. Falha barulhenta, que é o certo, mas vale saber.

Uma collection ou várias?

Vários stores são para contextos estáticos e poucos, declarados no código. Para contexto dinâmico — por usuário, por sessão, por tenant — use uma collection só e separe pelo payload: 

// dinâmico: uma collection, filtro no payload
await ctx.memory.conhecimento.remember(nota, { payload: { userId } });
await ctx.memory.conhecimento.recall(pergunta, { where: { userId } });
O Qdrant desaconselha muitas collections — limite de 1000 por cluster no Cloud, e overhead de recursos. Dezenas de contextos estáticos está tranquilo; milhares de usuários, não.

Trazendo o seu próprio banco

O contrato é o VectorStore, no mesmo modelo dos providers: a classe base cuida do transporte (retry, timeout) e você implementa a tradução para a API do seu backend. Tudo sai do @thenajs/core.

pgvector.store.ts
import { VectorStore } from "@thenajs/core";
import type {
  VectorStoreCredentials, VectorDocument, VectorMatch,
  VectorSearch, CollectionOptions,
} from "@thenajs/core";

export class PgVectorStore<C extends string = string> extends VectorStore<C> {
  public readonly collection: string;

  constructor(credentials: VectorStoreCredentials<C>) {
    super();
    this.configureTransport(credentials);   // ganha retry e timeout
    this.collection = credentials.collection ?? "thena_memory";
  }

  async ensureCollection(options: CollectionOptions) { /* … */ }
  async collectionExists() { /* … */ }
  async dropCollection() { /* … */ }
  async upsert(docs: VectorDocument[]) { /* … */ }
  async search(params: VectorSearch): Promise<VectorMatch[]> { /* … */ }
  async remove(selector: { ids?: (string | number)[] }) { /* … */ }
}
A base garanteVocê implementa
retry, backoff e timeout — via this.request() a tradução para a API do backend
criar a collection uma vez só, com as dimensões descobertas ensureCollection idempotente
o embed() e o formato do recall search devolvendo { id, score, payload } ordenado

Filtros seguem o mesmo padrão de sampling + raw dos providers: where para igualdade simples e rawFilter para o formato nativo do banco.

Sem o @Agent

VectorMemory funciona solto — é só a cola entre um provider e um store: 

import { VectorMemory } from "@thenajs/core";

const memoria = new VectorMemory({
  store: conhecimento,
  provider: new LocalOllamaProvider(),
});

await memoria.remember("o deploy roda pelo scripts/deploy.sh");
const achados = await memoria.recall("como faço deploy?", { limit: 3 });
O framework não decide quando buscar nem como formatar o resultado. No hook o contexto sempre entra; numa tool, o modelo decide se precisa. As duas formas são suas.
