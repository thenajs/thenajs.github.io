Memória vetorial

Busca semântica: o agente grava textos e recupera por similaridade, não por ordem. É o par que faltava para o embed() dos providers.

⚠️ Dois "memory" diferentes. O ctx.state.memory é o bucket string[] de contexto durável, projetado como mensagem system — entra sempre no prompt, na ordem que você colocou. A memória vetorial desta página é outra coisa: você grava muito e recupera só o relevante, por similaridade. Uma é lembrete, a outra é biblioteca.

Registrando o banco

Os stores vão no config, como classes. O framework instancia cada uma uma vez — uma conexão e um ensureCollection por store, independente de quantos agentes existem.

vector/qdrant.store.ts
import { QdrantStore } from "@thenajs/qdrant-client";

export class MeuQdrant extends QdrantStore {
  constructor() {
    super({
      url: "http://localhost:6333",
      collection: "conhecimento",
      datasets: ["persistent", "sessao"],   // opcional: valida os nomes
    });
  }
}
config.ts
export const config: ThenaConfig = {
  log: true,
  report: true,
  memory: [MeuQdrant],   // as classes; o framework instancia
};

Injeção no construtor

Nada a declarar no @Agent: quem quer memória pede no construtor, como as tools já fazem com o WorkflowRuntime. Os embeddings saem do provider do próprio agente.

explorer.agent.ts
@Agent({
  provider: LocalOllamaProvider,   // o embed() dele gera os vetores
  prompt: "./explorer.agent.md",
})
export class ExplorerAgent {
  constructor(private readonly memory: VectorMemory) {}

  async beforePrompt(prompt: string, ctx: AgentContext) {
    const pergunta = ctx.state.history.at(-1)?.content ?? "";
    const achados = await this.memory.recall(pergunta, {
      dataset: "persistent",
      limit: 3,
      scoreThreshold: 0.5,
    });

    if (!achados.length) return;   // undefined mantém o prompt

    return `${prompt}\n\n## Contexto\n${achados.map((a) => `- ${a.text}`).join("\n")}`;
  }

  async afterResponse(resposta: string) {
    await this.memory.remember(resposta, { dataset: "sessao" });
  }
}

Agentes que não usam memória simplesmente não escrevem construtor — o argumento extra é ignorado. Sem memory no config, o parâmetro chega undefined.

A injeção é posicional, não por tipo. reflect-metadata foi evitado de propósito: o esbuild (que o tsx usa no npm start) não emite design:paramtypes, então DI por tipo compilaria e quebraria em silêncio no dev.

Datasets: vários contextos, um banco

dataset é sempre opcional — omitido, usa "default": 

await this.memory.remember("um fato solto");              // grava no "default"
await this.memory.recall("pergunta");                     // busca no "default"
await this.memory.recall("pergunta", { dataset: null });  // busca em TODOS
await this.memory.forget({ dataset: "sessao" });          // limpa um dataset

Datasets não são collections separadas: são um campo do payload com índice dedicado. É a recomendação do próprio Qdrant — muitas collections geram overhead de recursos, e o Qdrant Cloud limita a 1000 por cluster. Por isso dataset: null consegue buscar através de todos, o que com collections exigiria N buscas e merge manual.

Declarar datasets nas credentials é opcional e faz o runtime recusar um nome que você não declarou, em vez de devolver zero resultados em silêncio: 

[thena] Dataset "persistnet" não declarado. Conhecidos: persistent, sessao.

Mais de um banco

Uma collection guarda um tamanho de vetor só. Se dois agentes usam modelos de embedding com dimensões diferentes (768 e 1536, por exemplo), eles precisam de stores separados — basta acrescentar ao array: 

memory: [QdrantNomic, QdrantOpenAI],

// agente de 768: recebe o primeiro
constructor(private readonly nomic: VectorMemory) {}

// agente de 1536: recebe os dois, usa o segundo
constructor(
  private readonly _naoUso: VectorMemory,
  private readonly openai: VectorMemory,
) {}
⚠️ A ordem do array é contrato. Reordenar troca qual store cada agente usa, e o TypeScript não acusa — os parâmetros têm o mesmo tipo VectorMemory. Acrescente sempre no fim, nunca no meio.

Se as dimensões forem incompatíveis, o erro aparece na primeira escrita. Se forem iguais, você grava na collection errada em silêncio.

Misturar dimensões num store só falha antes de gastar o embedding, com a causa em vez do erro cru do banco: 

[thena] Este store já foi preparado com 768 dimensões, mas agora recebeu
embeddings de 1536. Uma collection aceita um único tamanho de vetor — modelos
de embedding diferentes precisam de stores diferentes.

As dimensões são descobertas sozinhas

Ninguém deveria precisar saber de cabeça que nomic-embed-text é 768 e text-embedding-3-small é 1536. No primeiro remember, o tamanho sai do próprio vetor e a collection é criada com ele.

Aponte um modelo dedicado a embeddings com embedModel nas credentials do provider. Sem isso, o Ollama usa o mesmo modelo do chat — e a maioria dos modelos de chat não serve para embeddings.

Trazendo seu próprio banco

O contrato é o VectorStore, e tudo sai do @thenajs/core — mesmo modelo de escrever um provider. A classe base cuida do transporte (retry, timeout) e você traduz para a API do seu backend.

pgvector.store.ts
import { VectorStore } from "@thenajs/core";
import type { VectorStoreCredentials, VectorDocument, VectorMatch,
              VectorSearch, CollectionOptions } from "@thenajs/core";

export class PgVectorStore extends VectorStore {
  constructor(credentials: VectorStoreCredentials) {
    super();
    this.configureTransport(credentials);   // ganha retry e timeout
  }

  async ensureCollection(options: CollectionOptions) { /* … */ }
  async collectionExists() { /* … */ }
  async dropCollection() { /* … */ }
  async upsert(docs: VectorDocument[]) { /* … */ }
  async search(params: VectorSearch): Promise<VectorMatch[]> { /* … */ }
  async remove(selector: { ids?: (string | number)[] }) { /* … */ }
}

Filtros seguem o mesmo padrão de sampling + raw dos providers: where para igualdade simples e rawFilter para o formato nativo do banco, que vence quando presente.

Sem agente nenhum

VectorMemory funciona solto, se você quiser usar fora de um fluxo de agentes: 

import { VectorMemory } from "@thenajs/core";

const memoria = new VectorMemory({
  store: new MeuQdrant(),
  provider: new LocalOllamaProvider(),
});

await memoria.remember("o deploy roda pelo scripts/deploy.sh");
const achados = await memoria.recall("como faço deploy?", { limit: 3 });
// [{ text, score, dataset, id, payload }]
O @thenajs/qdrant-client é um cliente nativo sobre a API REST — sem SDK. Requer Qdrant 1.10 ou superior, porque o endpoint unificado /points/query estreou nessa versão.
